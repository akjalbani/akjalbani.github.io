01

Start Learner Lab and Create a VPC

The first thing you do in every lab session is start the AWS Academy Learner Lab, then create a dedicated VPC for this workshop. A VPC (Virtual Private Cloud) is your own private network inside AWS — all EC2 instances you create will live inside it. We will use the AWS VPC Wizard to create it in one step: it automatically provisions a public subnet and a private subnet for you.

Step 1

Start your AWS Academy Learner Lab session

Log in to your AWS Academy course and open the Learner Lab module. Click Start Lab. Wait until the circle indicator in the top-left corner turns green — this means AWS resources are ready. Then click the AWS link to open the AWS Management Console in a new browser tab.

⚠
Keep the Learner Lab tab open for the entire session

The session countdown timer runs inside that tab. If you close it, your session ends and all EC2 instances, VPCs, and data are deleted. Sessions last approximately 4 hours. If you need more time, click Start Lab again — note that this restarts the timer but also terminates your existing resources.

Step 2

Open the VPC service

In the AWS Management Console, type VPC in the search bar at the top and select VPC from the results. This opens the VPC Dashboard. You will create a new VPC from here — do not use or modify any existing default VPC that may be listed.

Step 3

Create a new VPC using the VPC and more wizard

On the VPC Dashboard, click Create VPC. At the top of the creation page, select the option labelled VPC and more — this is the wizard that creates the VPC, subnets, route tables, and internet gateway all in one step.

Configure the wizard with the following settings:

Click Create VPC. AWS will provision all resources automatically. When complete, you will see a success screen listing everything created.

ℹ
What the wizard creates for you

With the settings above, AWS automatically creates the following — you do not need to configure any of these manually:

  • VPC named splunk-workshop-vpc with CIDR 10.0.0.0/16
  • Public subnet named splunk-workshop-subnet-public1 with CIDR 10.0.0.0/24 — instances here get a public IP and can reach the internet
  • Private subnet named splunk-workshop-subnet-private1 with CIDR 10.0.128.0/24 — instances here have no public IP but can communicate with instances in the public subnet over private IPs
  • Internet Gateway — attached to the VPC, allows the public subnet to reach the internet
  • Route tables — one for the public subnet (routes internet traffic through the gateway), one for the private subnet (local traffic only)
Step 4

Enable auto-assign public IP on the public subnet

In the left menu, click Subnets. Find the subnet named splunk-workshop-subnet-public1. Click on it to open its details, then click Actions → Edit subnet settings. Tick the checkbox for Enable auto-assign public IPv4 address and click Save.

This ensures that any EC2 instance launched into the public subnet automatically receives a public IP address — which is required so you can open Splunk Web in your browser and connect to your instances using EC2 Instance Connect — directly from the AWS console, no SSH client needed.

ℹ
How the two subnets are used in this workshop
  • Public subnet (10.0.0.0/24) — the Splunk server (Instance 1) is placed here. It needs a public IP so you can open Splunk Web at http://<public-ip>:8000 from your browser.
  • Private subnet (10.0.128.0/24) — the web server (Instance 2) is placed here. It has no public IP. The Universal Forwarder on this instance sends logs to the Splunk server using the Splunk server's private IP address over the internal VPC network. This reflects a realistic SOC architecture where log sources sit in a protected network segment.

You will connect to the web server using EC2 Instance Connect from the AWS console — covered in Section 3.

✓
VPC setup complete

You now have a VPC named splunk-workshop-vpc with one public subnet and one private subnet. All resources in this lab will be launched into this VPC. Proceed to Section 2 to launch the Splunk server.

Installing Splunk Enterprise on EC2

This section launches the Splunk server — the machine that receives logs, indexes them, and serves the web interface. You will launch one EC2 instance, download Splunk directly from splunk.com, and run an installation script that configures everything automatically.

ℹ
Each participant needs their own Splunk download URL

Splunk requires a free account to access the download page. Do this once before the session:

  • Go to splunk.com/en_us/download/splunk-enterprise.html, select Linux → .deb, and copy the full URL from the wget command shown.
  • In the script below, replace the SPLUNK_DEB_URL value with your URL. That is the only line you need to change.

Step 3

Run the Splunk installation script

The script below downloads, installs, and fully configures Splunk Enterprise. The only line you need to change is SPLUNK_DEB_URL — replace the example URL with the one from your splunk.com account (see the callout above).

In the Splunk server browser terminal (EC2 Instance Connect), create and run the script. The only line to edit is SPLUNK_DEB_URL — replace it with the URL from your splunk.com account.

# ================================================================

# Replace the URL below with the one from your splunk.com account
SPLUNK_DEB_URL="https://download.splunk.com/products/splunk/releases/10.x.0/linux/splunk-10.x.0-f798d4d4xxxx-linux-amd64.deb"
# ────────────────────────────────────────────────────────────────────────

# Filename is extracted automatically from the URL — do not edit this line
SPLUNK_PKG=$(basename "${SPLUNK_DEB_URL}")
SPLUNK_HOME="/opt/splunk"
ADMIN_PASS="Workshop2026!"

echo "[1/6] Updating system packages..."
sudo apt-get update -qq
sudo apt-get install -y wget curl ufw net-tools

echo "[2/6] Downloading Splunk Enterprise..."

echo "[4/6] Starting Splunk and accepting the licence..."

# This is expected and safe in a lab environment. Splunk still starts correctly.

  --run-as-root \
  --seed-passwd "${ADMIN_PASS}"

# Register Splunk as a systemd service so it survives reboots
sudo "${SPLUNK_HOME}"/bin/splunk enable boot-start \
  --accept-license --answer-yes --no-prompt \
  --run-as-root

echo "[5/6] Opening forwarder receiver port and creating indexes..."
# Port 9997 receives log data from the Universal Forwarder on the web server
sudo "${SPLUNK_HOME}"/bin/splunk enable listen 9997 \
  --run-as-root \
  -auth admin:"${ADMIN_PASS}"

# Separate indexes keep web server logs and security logs organised
sudo "${SPLUNK_HOME}"/bin/splunk add index webserver_logs \
  --run-as-root \
  -auth admin:"${ADMIN_PASS}"

sudo "${SPLUNK_HOME}"/bin/splunk add index security_logs \
  --run-as-root \
  -auth admin:"${ADMIN_PASS}"

echo "[6/6] Configuring firewall..."
sudo ufw allow 22/tcp     # SSH
sudo ufw allow 8000/tcp   # Splunk Web UI
sudo ufw allow 9997/tcp   # Forwarder receiver
sudo ufw allow 8089/tcp   # Splunk management API
sudo ufw --force enable

ℹ
What is 169.254.169.254?

This address is the AWS Instance Metadata Service — a special internal endpoint that exists only inside AWS. No traffic goes to the internet. The EC2 instance is asking AWS: "What is my own public IP address?" AWS responds with a single line of text, e.g. 54.210.33.107. The script captures this and prints it at the end so you know exactly which URL to open in your browser.

⚠
Change the admin password after first login

The script sets a shared workshop password for convenience. Once logged in, go to Settings → Access Controls → Users → admin → Edit and set a personal password before conducting any real monitoring work.

✓
Expected result

The script prints a summary at the end showing your Splunk Web URL. Open that URL in your browser — you should see the Splunk login page. Log in with username admin and password Workshop2026!.

If Splunk was previously installed and the script failed, clean up first: sudo /opt/splunk/bin/splunk stop, then sudo apt-get remove splunk -y && sudo rm -rf /opt/splunk, then re-run the script.

03

Deploying the Web Server and Universal Forwarder

In this section you will launch a second EC2 instance using Amazon Linux 2023 into the public subnet. Rather than SSH-ing in and running scripts manually, everything is automated using EC2 User Data — a startup script that AWS runs automatically the first time the instance boots. By the time the instance reaches Running state, Apache, PHP, the demo web application, and the Splunk Universal Forwarder will all be installed and configured.

ℹ
Before you start — two values you need

Open a notepad and record these two values now. You will paste them into the User Data script in Step 2:

  • Splunk Server Private IP — go to EC2 console, click on Instance 1 (splunk-server), and copy the Private IPv4 address. It looks like 10.0.0.x. The forwarder uses this to send logs to Splunk over the VPC internal network.
  • Universal Forwarder download URL — log in to splunk.com, go to splunk.com/en_us/download/universal-forwarder, select Linux → RPM package (Amazon Linux 2023 uses RPM, not .deb), and copy the full URL from the wget command shown.

In the EC2 console, click Launch Instance. Configure it exactly as follows:

ℹ
Why public subnet for the web server?

We place the web server in the public subnet so that attack traffic sent from the Splunk server browser terminal can reach it directly over HTTP on port 80 — this is what makes the brute force, SQL injection, and directory traversal demonstrations visible and realistic. The Splunk server is also in the public subnet, and both instances communicate with each other using their private IP addresses within the VPC — the forwarder never uses the public IP to send logs.

Do not click Launch Instance yet. Continue to Step 2 to add the User Data script before launching.

Step 2

Add the User Data script

Scroll down on the Launch Instance page to the Advanced details section and expand it. At the very bottom you will find a field labelled User data. Paste the entire script below into that field.

Before pasting — replace the two values marked in amber:

  • Replace <SPLUNK-SERVER-PRIVATE-IP> with the private IP of Instance 1 (e.g. 10.0.0.45)
  • Replace the UF_RPM_URL value with your personal Universal Forwarder RPM download URL from splunk.com
⚠
Select the RPM package, not .deb

On the Universal Forwarder download page at splunk.com, select Linux → RPM. Amazon Linux uses RPM packages. The .deb package is for Ubuntu and will not install.

bash — paste into EC2 User Data field (Advanced details)
#!/bin/bash
# ================================================================
#  Web Server + Splunk Universal Forwarder — EC2 User Data
#  AMI: Amazon Linux 2023
#
#  BEFORE PASTING — replace these two lines:
#
#  1.  SPLUNK_IP   — private IP of your Splunk server (Instance 1)
#                   EC2 console → Instance 1 → Private IPv4 address
#                   e.g.  10.0.0.45
#
#  2.  UF_RPM_URL  — your Universal Forwarder download URL
#                   splunk.com → Downloads → Universal Forwarder
#                   → Linux → RPM → copy the URL from the wget command
# ================================================================

SPLUNK_IP="<SPLUNK-SERVER-PRIVATE-IP>"
UF_RPM_URL="https://download.splunk.com/products/universalforwarder/releases/10.x.0/linux/splunkforwarder-10.x.0-f798d4d4xxxx.x86_64.rpm"

# ── Step 1: Install Apache, PHP, and rsyslog ─────────────────────
# rsyslog is required on Amazon Linux 2023 — it does not ship with
# rsyslog by default. Without it /var/log/secure does not exist
# and index=security_logs will show zero events in Splunk.
yum update -y
yum install -y httpd php rsyslog

systemctl enable rsyslog
systemctl start rsyslog

# ── Step 2: Create the demo login page ───────────────────────────
cat > /var/www/html/login.php << 'PHPEOF'
<?php
  $user = $_GET['user'] ?? '';
  $pass = $_GET['pass'] ?? '';
  echo "<h2>Workshop Demo Login</h2>";
  echo "<p>Username: " . htmlspecialchars($user, ENT_QUOTES) . "</p>";
PHPEOF

mkdir -p /var/www/html/admin /var/www/html/backup
echo "Restricted" > /var/www/html/admin/config.txt

# ── Step 3: Enable SSH password authentication ────────────────────
# Amazon Linux 2023 disables password auth by default.
# Enabling it allows the brute force demonstration in Section 6
# to generate real failed login entries in /var/log/secure.
sed -i 's/PasswordAuthentication no/PasswordAuthentication yes/' /etc/ssh/sshd_config
sed -i 's/PasswordAuthentication no/PasswordAuthentication yes/' /etc/ssh/sshd_config.d/*.conf 2>/dev/null || true
systemctl restart sshd

# ── Step 4: Start Apache ─────────────────────────────────────────
systemctl enable httpd
systemctl start httpd

# ── Step 5: Fix log file permissions ─────────────────────────────
# Pre-create Apache log files so the forwarder can monitor them
# immediately. Apache only creates them on the first HTTP request.
touch /var/log/httpd/access_log /var/log/httpd/error_log
chmod 644 /var/log/httpd/access_log /var/log/httpd/error_log

# Give rsyslog 3 seconds to create /var/log/secure after starting,
# then set group-read so the splunkfwd user can tail it.
sleep 3
touch /var/log/secure
chmod 640 /var/log/secure
chown root:adm /var/log/secure

# ── Step 6: Download and install the Universal Forwarder ─────────
UF_PKG=$(basename "${UF_RPM_URL}")
wget -q "${UF_RPM_URL}" -O /tmp/"${UF_PKG}"
rpm -i --nosignature /tmp/"${UF_PKG}"

# Add splunkfwd (created by the RPM) to adm group so it can
# read /var/log/secure — must run after rpm -i creates the user
usermod -aG adm splunkfwd

# ── Step 7: Write outputs.conf — where to send logs ──────────────
mkdir -p /opt/splunkforwarder/etc/system/local

cat > /opt/splunkforwarder/etc/system/local/outputs.conf << EOF
[tcpout]
defaultGroup = splunk_indexer

[tcpout:splunk_indexer]
server = ${SPLUNK_IP}:9997
EOF

# ── Step 8: Write inputs.conf — which files to monitor ───────────
cat > /opt/splunkforwarder/etc/system/local/inputs.conf << 'EOF'
[monitor:///var/log/httpd/access_log]
index = webserver_logs
sourcetype = apache_access

[monitor:///var/log/httpd/error_log]
index = webserver_logs
sourcetype = apache_error

[monitor:///var/log/secure]
index = security_logs
sourcetype = linux_secure
EOF

# ── Step 9: Start the forwarder ──────────────────────────────────
# Reads outputs.conf and inputs.conf automatically on startup.
/opt/splunkforwarder/bin/splunk start \
  --accept-license --answer-yes --no-prompt \
  --seed-passwd "Forwarder2026!"

# Enable auto-start on reboot
/opt/splunkforwarder/bin/splunk enable boot-start \
  --accept-license --answer-yes --no-prompt
ℹ
How User Data works

AWS runs the User Data script automatically as root the first time the instance boots. You do not SSH in or run anything manually — Apache, the demo app, and the Splunk Forwarder are all installed and configured within 2–3 minutes of the instance reaching Running state.

To confirm it completed: in the web server browser terminal, run sudo tail -20 /var/log/cloud-init-output.log. The last line should read Cloud-init finished.

After pasting the script into the User Data field, click Launch Instance.

Step 3

Verify the web server and forwarder are running

Wait approximately 3 minutes after the instance reaches Running state for the User Data script to complete. Then verify each component:

Verify Apache: Open a new browser tab and go to http://<WEBSERVER-PUBLIC-IP>/login.php?user=test&pass=test — replacing <WEBSERVER-PUBLIC-IP> with the public IP of Instance 2 shown in the EC2 console. You should see a page displaying Username attempted: test.

Verify the forwarder in Splunk using the two methods below. Note that Settings → Forwarder Management will not appear in a fresh Splunk install — it requires the Deployment Server feature which is not needed for this workshop. Use Method 1 and Method 2 instead.

Method 1

Run a search in Splunk Web — fastest check

In Splunk Web, click Search & Reporting. Set the time range to Last 60 minutes and run the query below. If log events appear, the forwarder is connected and sending data successfully.

SPL — Method 1: confirm logs are arriving
index=webserver_logs | head 5

Each result is one Apache HTTP request logged by the web server and forwarded to Splunk. If you see results, proceed to Section 5. If no results appear after 5 minutes, continue to Method 2 to diagnose the connection.

Method 2

Check the active connection on the Splunk server

In the Splunk server browser terminal (Instance 1), run the two commands below. They check whether the Splunk forwarder receiver port is open and whether the web server has established a connection to it.

bash — Splunk server browser terminal (Instance 1)
# Check that Splunk is listening on port 9997 (the forwarder receiver port)
sudo ss -tnp | grep 9997

# Expected output when the web server is connected:
# LISTEN  0  128  0.0.0.0:9997  ...  (Splunk is ready to receive)
# ESTAB   0  0    10.0.0.x:9997  10.0.0.y:xxxxx  (active connection from web server)
bash — confirm the forwarder receiver is enabled in Splunk
# Lists all enabled receiving ports — should show port 9997
sudo /opt/splunk/bin/splunk list forward-server --run-as-root
ℹ
Reading the ss output

Look for two lines referencing port 9997. A line with state LISTEN means Splunk is waiting for connections. A line with state ESTAB (established) means the web server forwarder has connected. The web server's private IP (10.0.0.x) will appear in the ESTAB line. If you only see LISTEN but no ESTAB, the forwarder on the web server has not connected yet — wait another minute and re-run, or check the User Data log in the web server browser terminal with sudo tail -30 /var/log/cloud-init-output.log.

✓
Expected result

The SPL query returns the 5 most recent Apache log entries from the web server. Each event represents one HTTP request — the visit to login.php you made above will appear here.

Also run index=security_logs | head 5 to confirm the auth log is being forwarded. Results may be sparse until the brute force demonstration in Section 6 generates SSH login attempts — a few existing SSH session entries from your own login will appear if the forwarder is working correctly.

⚠
If the query returns no results after 5 minutes

Run sudo tail -30 /var/log/cloud-init-output.log on the web server. Common issues:

  • index=security_logs returns zero events — confirm rsyslog is running on the web server (sudo systemctl status rsyslog) and that /var/log/secure exists. The User Data script installs and starts rsyslog automatically.
  • Forwarder not connecting to Splunk — confirm SPLUNK_IP is the correct private IP of Instance 1 and that port 9997 is open in the Splunk server security group.
  • No web server response on port 80 — confirm the security group allows HTTP and that the instance has a public IP assigned.
  • Script did not complete — if the RPM download failed, confirm UF_RPM_URL is a valid RPM URL (ends in .x86_64.rpm, not .deb).
04

Splunk Architecture Overview

Now that both instances are running, it is useful to see how they relate to each other. The diagram below reflects exactly what you have deployed — data flows from the web server on the right, through the forwarder agent, across the private VPC network to the Splunk indexer, and up to the search interface you access in your browser.

Data Sources
Apache access log  ·  Apache error log  ·  /var/log/secure
Generated on EC2 Instance 2 (webserver — Amazon Linux 2023) at /var/log/httpd/ and /var/log/secure
↓   Tailed continuously by the agent on the same machine
Universal Forwarder
Lightweight agent — EC2 Instance 2 (webserver, Amazon Linux 2023, public subnet)
Sends logs over TCP port 9997 to the Splunk server's private IP (10.0.0.x) within the VPC — installed automatically via User Data on first boot
↓   Encrypted stream over the VPC internal network — both instances in public subnet 10.0.0.0/24, communicating via private IPs
Indexer
Splunk Enterprise — EC2 Instance 1 (splunk-server)
Receives, parses, timestamps, and stores events in the webserver_logs and security_logs indexes
↓   SPL queries run against stored index data
Search Head
Splunk Web — EC2 Instance 1, port 8000
Dashboards, alerts, and the SPL search bar — accessed from your browser at http://<SPLUNK-PUBLIC-IP>:8000

In this workshop the Indexer and Search Head are co-located on the same instance — called a standalone deployment. This is appropriate for labs. In production, these roles run on separate dedicated servers to distribute the query load.

05

SPL Fundamentals

Search Processing Language (SPL) is the query language built into Splunk. It follows a pipeline model — each command receives the output of the previous one, separated by a pipe character (|). Run the queries below in order in Splunk Web. Go to Search & Reporting and set the time range to Last 15 minutes before running each one.

Query 1

Confirm log data is arriving

SPL
index=webserver_logs | head 20

You should see the 20 most recent HTTP requests logged by Apache. Each line is one event — one web request.

Query 2

Count events by HTTP status code

SPL
index=webserver_logs sourcetype=apache_access
| stats count by status
| sort -count
Query 3

Plot event volume over time

SPL
index=webserver_logs
| timechart span=1m count
Query 4

Extract a field from raw text using rex

The rex command extracts fields from unstructured text using named regex capture groups. This is essential for logs Splunk has not automatically parsed.

SPL
index=security_logs sourcetype=linux_secure
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| stats count by src_ip
| sort -count

Attack Demonstrations and Detection

The following three demonstrations simulate attack patterns a SOC analyst encounters regularly. Each follows the same structure: run the attack against the web server, then switch to Splunk Web and run the detection query to find the evidence in the logs.

⚠
Authorised use only

Run these commands exclusively against EC2 Instance 2 (webserver) within your own AWS Academy Learner Lab environment. Executing these commands against any system you do not own or have explicit permission to test is illegal. This lab exists solely for education.

Attack 1

SSH Brute Force

A brute force attack systematically tries many passwords against an authentication service. The tool hydra automates this. Every failed attempt writes a Failed password entry to /var/log/auth.log on the web server, which the forwarder ships to Splunk's security_logs index.

Run the attack from the Splunk server browser terminal (Instance 1). Target the web server's public IP on port 22. Password authentication is enabled on the web server via User Data — each failed attempt writes a Failed password entry to /var/log/secure and flows into Splunk in real time.

bash — Splunk server browser terminal (Instance 1)
# Install hydra on the Splunk server
sudo apt-get install -y hydra

# Create a small wordlist of passwords to try
cat > /tmp/wordlist.txt << EOF
password
123456
admin
letmein
workshop
splunk
amazon
ec2user
Password1
Welcome1
EOF

# Run the brute force — replace <WEBSERVER-PUBLIC-IP> with the public IP of Instance 2
hydra -l ec2-user -P /tmp/wordlist.txt \
  ssh://<WEBSERVER-PUBLIC-IP> \
  -t 4 -vV 2>&1 | tail -30

Wait for hydra to finish, then switch to Splunk Web and run this detection query:

SPL — Detect SSH Brute Force
index=security_logs sourcetype=linux_secure "Failed password"
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| rex field=_raw "for (?:invalid user )?(?P<username>\w+)"
| stats
    count            as attempts
    dc(username)      as usernames_tried
    earliest(_time)  as first_seen
    latest(_time)    as last_seen
    by src_ip
| where attempts > 3
| eval duration_sec = last_seen - first_seen
| eval severity = case(
    attempts > 50, "CRITICAL",
    attempts > 20, "HIGH",
    attempts > 5,  "MEDIUM",
    true(),          "LOW")
| sort -attempts
| table src_ip, attempts, usernames_tried, severity, duration_sec
Attack 2

SQL Injection

SQL injection sends malicious SQL syntax as a URL parameter. Even when the application rejects the input, Apache logs the full request URI — including the injected payload — in /var/log/httpd/access_log. Run from the Splunk server browser terminal (Instance 1).

bash — Splunk server browser terminal (Instance 1)
# Replace <WEBSERVER-PUBLIC-IP> with the public IP of Instance 2
TARGET="http://<WEBSERVER-PUBLIC-IP>"

payloads=(
  "' OR '1'='1"
  "' OR 1=1--"
  "' UNION SELECT NULL,NULL--"
  "admin'--"
  "1; DROP TABLE users--"
  "' AND SLEEP(5)--"
  "' OR 'x'='x"
)

for payload in "${payloads[@]}"; do
  encoded=$(python3 -c "import urllib.parse,sys; print(urllib.parse.quote(sys.argv[1]))" "${payload}")
  http_code=$(curl -s -o /dev/null -w "%{http_code}"     "${TARGET}/login.php?user=${encoded}&pass=test")
  echo "HTTP ${http_code}  →  ${payload}"
  sleep 0.5
done

You should see HTTP 200 for every payload — this confirms the requests reached Apache and were logged. Now switch to Splunk Web to find them.

ℹ
Run the diagnostic query first

Splunk auto-extracts a uri_query field from Apache logs, but on Amazon Linux 2023 with sourcetype=apache_access this field is often empty. The detection query below reads directly from _raw using rex — it always works regardless of which fields Splunk has parsed. First run the diagnostic below to confirm your events are present, then run the detection query.

SPL — Step 1: confirm events exist (run first)
index=webserver_logs sourcetype=apache_access
| head 5
| table _time, _raw

You should see raw Apache log lines containing login.php?user= followed by the URL-encoded payloads. If you see these events, the detection query below will find them.

SPL — Step 2: detect SQL injection from raw logs
index=webserver_logs sourcetype=apache_access
| rex field=_raw "GET (?P<full_uri>[^ ]+)"
| eval decoded = urldecode(full_uri)
| where match(decoded, "(?i)(union|select|drop|sleep|or 1=1|admin)")
| eval src_ip = coalesce(clientip, mvindex(split(_raw," "),0))
| stats
    count            as injection_attempts
    values(decoded) as payloads_seen
    by src_ip
| sort -injection_attempts
Attack 3

Directory Traversal

A directory traversal attack uses ../ sequences — sometimes URL-encoded — to try to access files outside the web root such as /etc/passwd. Apache logs every attempt in /var/log/httpd/access_log even when it returns 404. Run from the Splunk server browser terminal (Instance 1).

bash — Splunk server browser terminal (Instance 1)
# Replace <WEBSERVER-PUBLIC-IP> with the public IP of Instance 2
TARGET="http://<WEBSERVER-PUBLIC-IP>"

traversal_paths=(
  "../../../../etc/passwd"
  "../../../etc/shadow"
  "..%2F..%2F..%2Fetc%2Fpasswd"
  "%2e%2e%2f%2e%2e%2fetc%2fpasswd"
  "....//....//etc/passwd"
  "/admin/../../../etc/passwd"
)

for path in "${traversal_paths[@]}"; do
  http_code=$(curl -s -o /dev/null -w "%{http_code}" "${TARGET}/${path}")
  echo "HTTP ${http_code}  →  ${path}"
  sleep 0.3
done

HTTP 404 responses are expected — Apache correctly blocks the traversal but still logs every attempt. The log entry is what matters for detection.

ℹ
Run the diagnostic query first

The fields uri, uri_query, and clientip are not reliably auto-extracted by Splunk when using sourcetype=apache_access on Amazon Linux 2023. The detection query below reads directly from _raw using rex — the same approach that works for Attack 2.

SPL — Step 1: confirm traversal events exist
index=webserver_logs sourcetype=apache_access
| rex field=_raw "GET (?P<full_uri>[^ ]+)"
| eval decoded = urldecode(full_uri)
| where like(decoded, "%etc%") OR like(decoded, "%shadow%")
| table _time, _raw

You should see log lines containing passwd or shadow in the URI. If these appear, the detection query below will find them.

SPL — Step 2: detect directory traversal attempts
index=webserver_logs sourcetype=apache_access
| rex field=_raw "^(?P<src_ip>\S+) "
| rex field=_raw "GET (?P<full_uri>[^ ]+)"
| rex field=_raw " (?P<status>\d{3}) "
| eval decoded = urldecode(full_uri)
| where match(decoded, "[.][.][/\\]")
    OR match(full_uri, "%2e%2e|%252e|2[Ff]\.\.")
| stats
    count                 as traversal_attempts
    values(decoded)       as paths_tried
    values(status)        as http_responses
    by src_ip
| eval risk_score = traversal_attempts * 10
| sort -traversal_attempts

Incident Response Workflow

Detection is only the first step. A mature SOC follows a structured process to investigate, contain, and document each incident. The table below maps each phase of incident response to the action taken in Splunk and the AWS console.

PhaseSOC ActionTool Used
1. DetectionScheduled alert fires — 10+ failed SSH attempts from one IP in 5 minutesSplunk alert configured under Settings → Alerts
2. TriageAnalyst reviews alert severity, confirms the IP is not an internal scannerSplunk dashboard — top attacker IPs panel
3. InvestigationDetermine whether any attempt succeeded and which accounts were targetedSPL query below — checks for successful logins from the attacker IP
4. ContainmentBlock the attacking IP at the security group levelAWS Console → EC2 → Security Groups → Edit inbound rules → Deny the IP
5. DocumentationRecord the timeline, affected systems, and actions takenExport SPL results to CSV; attach to ITSM ticket
6. Post-IncidentReview alert thresholds, harden SSH configuration, consider fail2banDashboard used in debrief to replay the event timeline
SPL

Check whether a brute force attack succeeded

Run this query during the Investigation phase. If the result set is not empty, a compromise may have occurred and the account should be locked immediately.

SPL — Successful Login After Failed Attempts
index=security_logs sourcetype=linux_secure
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| eval outcome = case(
    searchmatch("Failed password"),   "failure",
    searchmatch("Accepted password"), "success",
    true(), "other")
| stats
    sum(eval(outcome="failure")) as failures
    sum(eval(outcome="success")) as successes
    by src_ip
| where failures > 3 AND successes > 0
| eval alert = "POTENTIAL COMPROMISE — investigate immediately"
