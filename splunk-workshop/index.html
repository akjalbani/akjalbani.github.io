01

Create a VPC and Subnets

Before launching any EC2 instances, you need a Virtual Private Cloud (VPC) — an isolated network inside AWS where all your lab resources will live. Both the Splunk server and the web server will be placed in the same public subnet so they can communicate with each other over private IP addresses and be accessible from your browser via their public IPs.

ℹ
What is a VPC?

A VPC (Virtual Private Cloud) is your own private section of the AWS network. Think of it as renting a floor in a data centre — you control what goes in, what comes out, and how the machines on that floor talk to each other. Without a VPC, you cannot launch EC2 instances.

Every AWS account comes with a default VPC pre-created in each region. AWS Academy Learner Lab provides this default VPC automatically. You do not need to build one from scratch — the steps below confirm it exists and note the values you will need later.

Step 1

Start your AWS Academy Learner Lab session

Log in to your AWS Academy course, open the Learner Lab module, and click Start Lab. Wait until the circle indicator in the top-left turns green, then click AWS to open the AWS Management Console in a new tab.

⚠
Do not close the Learner Lab tab

The session timer runs in that tab. If you close it, your session may terminate and all EC2 instances and data will be lost. Sessions last approximately 4 hours.

Step 2

Locate the default VPC

In the AWS Console, use the search bar at the top to search for VPC and open the VPC service. In the left menu, click Your VPCs.

You will see a VPC listed with the name default. This is the pre-built VPC provided by AWS Academy. Note the following values — you will not need to enter them anywhere manually, but understanding them helps:

FieldTypical ValueWhat it means
VPC IDvpc-xxxxxxxxxThe unique identifier for this network — AWS assigns it automatically
IPv4 CIDR172.31.0.0/16The IP address range for your entire VPC — supports up to 65,536 addresses
StateAvailableConfirms the VPC is active and ready to use
Step 3

Confirm a public subnet exists

In the left menu, click Subnets. You will see one or more subnets already listed — these belong to the default VPC. Identify any subnet in the us-east-1a availability zone (or the first zone listed in your region). Note its Subnet ID and confirm Auto-assign public IPv4 is set to Yes.

If Auto-assign public IPv4 is set to No, click the subnet, then Actions → Edit subnet settings and enable it. This ensures any EC2 instance launched into this subnet automatically receives a public IP address — which is required to access Splunk Web from your browser.

✓
You are ready to proceed

You now have a VPC and a public subnet. Both EC2 instances you create in the next sections will be launched into this same subnet, giving them private IPs to communicate with each other and public IPs so you can access them from your laptop.

02

Installing Splunk Enterprise on EC2

This section launches the Splunk server — the machine that receives logs, indexes them, and serves the web interface. You will launch one EC2 instance, download Splunk directly from splunk.com, and run an installation script that configures everything automatically.

ℹ
Before you run the script — get the Splunk download URL

Splunk requires a free account before it shows you the download link. Do this once before the workshop session:

  • Go to splunk.com and create a free account (email only, no credit card).
  • Navigate to splunk.com/en_us/download/splunk-enterprise.html.
  • Select Linux → .deb package. Splunk will display a ready-made wget command.
  • From that command, copy the version number (e.g. 9.2.1) and the build hash (e.g. 78803f08aabb) — these are the two values highlighted in amber in the script below.
  • Update those two variables in the script before running it.

The download URL does not require a logged-in session — once you have it, wget downloads the file directly to EC2 with no browser needed.

Step 1

Launch EC2 Instance 1 — Splunk Server

In the AWS Console, search for EC2 and open the service. Click Launch Instance and configure it exactly as follows:

  • Public IPv4 address — you will open Splunk Web at this address
  • Private IPv4 address — the forwarder will send logs to this address in Section 3
Step 2

Connect to the instance via SSH

Download the labsuser.pem key file from the Learner Lab panel (there is a download link on the left side of the lab page). Then open a terminal on your laptop and run:

bash — your laptop terminal
# Step 1: Set the correct permissions on the key file (required by SSH)
chmod 400 ~/Downloads/labsuser.pem

# Step 2: Connect to the Splunk server
# Replace <SPLUNK-PUBLIC-IP> with the Public IPv4 address you recorded above
ssh -i ~/Downloads/labsuser.pem ubuntu@<SPLUNK-PUBLIC-IP>

When prompted "Are you sure you want to continue connecting?", type yes and press Enter. You are now inside the Splunk server.

Step 3

Run the Splunk installation script

The script below downloads, installs, and fully configures Splunk Enterprise. Before running it, update the two values highlighted in amber to match the version and build hash from the splunk.com download page (see the note above).

Copy the entire script, paste it into your SSH session, and press Enter. It takes approximately 3–5 minutes to complete.

bash — paste into the Splunk server SSH session
#!/bin/bash
# ================================================================
#  Splunk Enterprise — Automated Installation Script
#  Run on: EC2 Instance 1 (splunk-server) — Ubuntu 22.04
#
#  BEFORE RUNNING:
#  Update SPLUNK_VERSION and SPLUNK_BUILD to match the values
#  shown on splunk.com/en_us/download/splunk-enterprise.html
#  (Linux > .deb package > copy the wget command shown there)
# ================================================================
set -euo pipefail

# ── UPDATE THESE TWO VALUES from splunk.com before running ──────
SPLUNK_VERSION="9.2.1"             # e.g. "9.2.1" — from the download page
SPLUNK_BUILD="78803f08aabb"       # e.g. "78803f08aabb" — from the download URL
# ────────────────────────────────────────────────────────────────

# Admin password for Splunk Web login (change after first login)
ADMIN_PASS="Workshop2026!"

SPLUNK_HOME="/opt/splunk"
PKG="splunk-${SPLUNK_VERSION}-${SPLUNK_BUILD}-linux-2.6-amd64.deb"
URL="https://download.splunk.com/products/splunk/releases/${SPLUNK_VERSION}/linux/${PKG}"

echo "[1/6] Updating system packages..."
sudo apt-get update -qq
sudo apt-get install -y wget curl ufw net-tools

echo "[2/6] Downloading Splunk Enterprise ${SPLUNK_VERSION}..."
wget -q --show-progress "${URL}" -O /tmp/"${PKG}"

echo "[3/6] Installing Splunk..."
sudo dpkg -i /tmp/"${PKG}"

echo "[4/6] Starting Splunk and accepting the licence..."
sudo "${SPLUNK_HOME}"/bin/splunk start \
  --accept-license --answer-yes --no-prompt \
  --seed-passwd "${ADMIN_PASS}"

# Enable Splunk to start automatically if the instance is rebooted
sudo "${SPLUNK_HOME}"/bin/splunk enable boot-start -user splunk

echo "[5/6] Enabling forwarder receiver port and creating log indexes..."
# Open port 9997 so the Universal Forwarder can send logs to this machine
sudo -u splunk "${SPLUNK_HOME}"/bin/splunk enable listen 9997 \
  -auth admin:"${ADMIN_PASS}"

# Create separate indexes to store web server logs and security logs
sudo -u splunk "${SPLUNK_HOME}"/bin/splunk add index webserver_logs \
  -auth admin:"${ADMIN_PASS}"

sudo -u splunk "${SPLUNK_HOME}"/bin/splunk add index security_logs \
  -auth admin:"${ADMIN_PASS}"

echo "[6/6] Configuring firewall..."
sudo ufw allow 22/tcp     # SSH
sudo ufw allow 8000/tcp   # Splunk Web
sudo ufw allow 9997/tcp   # Forwarder receiver
sudo ufw allow 8089/tcp   # Management API
sudo ufw --force enable

# Retrieve this instance's public IP from AWS instance metadata
PUBLIC_IP=$(curl -s http://169.254.169.254/latest/meta-data/public-ipv4)

echo ""
echo "================================================================"
echo "  Installation complete."
echo "  Open this URL in your browser:"
echo "  Splunk Web  →  http://${PUBLIC_IP}:8000"
echo "  Username    →  admin"
echo "  Password    →  ${ADMIN_PASS}"
echo "================================================================"
ℹ
What is 169.254.169.254?

This address is the AWS Instance Metadata Service — a special internal endpoint that exists only inside AWS. No traffic goes to the internet. The EC2 instance is asking AWS: "What is my own public IP address?" AWS responds with a single line of text, e.g. 54.210.33.107. The script captures this and prints it at the end so you know exactly which URL to open in your browser.

⚠
Change the admin password after first login

The script sets a shared workshop password for convenience. Once logged in, go to Settings → Access Controls → Users → admin → Edit and change it before conducting any real monitoring work.

✓
Expected result

Open your browser and go to http://<SPLUNK-PUBLIC-IP>:8000. You should see the Splunk login page. Log in with username admin and password Workshop2026!. The Splunk home screen confirms installation is complete.

03

Deploying the Universal Forwarder and Web Server

The Universal Forwarder (UF) is a lightweight Splunk agent installed on a source machine. It monitors log files and ships them over the network to the Splunk indexer on port 9997. In this section you will launch a second EC2 instance, install an Apache web server on it to generate realistic HTTP logs, and then install and configure the forwarder to send those logs — plus the system authentication log — to the Splunk server from Section 2.

ℹ
Two IP addresses to keep track of

This section involves two EC2 instances. Keep a notepad open with the following values — you will need to substitute them into the forwarder script:

  • Splunk Server Private IP — the private IPv4 address of Instance 1 (splunk-server). Find it in the EC2 console under Instance 1's detail page. It looks like 172.31.x.x. The forwarder uses this address to reach the Splunk indexer within the VPC.
  • Web Server Public IP — the public IPv4 address of Instance 2 (webserver). You will use this to SSH in and to send attack traffic in Section 6.

Launch EC2 Instance 2 — Web Server

Return to the EC2 console and click Launch Instance again. This is a separate, second instance — do not modify Instance 1. Configure it as follows:

Step 3

Install Apache and deploy the demo web application

While connected to the web server (Instance 2), run the script below. No values need to be changed in this script — copy and paste it as-is.

bash — paste into the webserver SSH session
#!/bin/bash
# ================================================================
#  Web Server Setup Script
#  Run on: EC2 Instance 2 (webserver) — Ubuntu 22.04
#  No values need to be changed in this script.
# ================================================================
set -euo pipefail

echo "[1/3] Installing Apache web server and PHP..."
sudo apt-get update -qq
sudo apt-get install -y apache2 php libapache2-mod-php

echo "[2/3] Deploying demo login page..."
# This simple PHP page logs all login attempts to Apache's access log.
# It is intentionally basic — its purpose is to generate HTTP log entries
# for the attack demonstrations in Section 6.
sudo tee /var/www/html/login.php << 'EOF'
<?php
$user = $_GET['user'] ?? '';
$pass = $_GET['pass'] ?? '';
if ($user !== '' && $pass !== '') {
    error_log("Login attempt received for user: $user");
}
echo "<!DOCTYPE html><html><body>";
echo "<h2>Workshop Demo Login</h2>";
echo "<p>Attempted username: " . htmlspecialchars($user, ENT_QUOTES) . "</p>";
echo "</body></html>";
EOF

echo "[3/3] Creating demo directories and starting Apache..."
# Create directories that will be targeted during the traversal demonstration
sudo mkdir -p /var/www/html/admin /var/www/html/backup
echo "Restricted — do not access" | sudo tee /var/www/html/admin/config.txt

sudo systemctl enable apache2
sudo systemctl restart apache2

WEB_IP=$(curl -s http://169.254.169.254/latest/meta-data/public-ipv4)
echo ""
echo "================================================================"
echo "  Apache is running."
echo "  Test page  →  http://${WEB_IP}/login.php?user=test&pass=test"
echo "================================================================"

Step 4

Install and configure the Universal Forwarder

Still connected to the web server (Instance 2), run the forwarder script below.

You must replace one value before running: find the line starting with SPLUNK_PRIVATE_IP and replace <SPLUNK-SERVER-PRIVATE-IP> with the private IPv4 address of Instance 1 (splunk-server). Find this in the EC2 console on Instance 1's detail page — it begins with 172.31.

Also update UF_VERSION and UF_BUILD to match the Universal Forwarder version available on splunk.com (same process as Section 2 — go to splunk.com/en_us/download/universal-forwarder, select Linux .deb, and copy the version and build hash from the displayed wget command).

bash — paste into the webserver SSH session
#!/bin/bash
# ================================================================
#  Universal Forwarder Installation Script
#  Run on: EC2 Instance 2 (webserver) — Ubuntu 22.04
#
#  BEFORE RUNNING — replace the values marked below:
#    1. SPLUNK_PRIVATE_IP  — private IP of your splunk-server (Instance 1)
#    2. UF_VERSION         — from splunk.com/en_us/download/universal-forwarder
#    3. UF_BUILD           — from the same download page (build hash in the URL)
# ================================================================
set -euo pipefail

# ── REPLACE THIS: Private IP of Instance 1 (splunk-server) ─────
SPLUNK_PRIVATE_IP="<SPLUNK-SERVER-PRIVATE-IP>"
# Example: SPLUNK_PRIVATE_IP="172.31.24.105"
# Find this in EC2 console > Instance 1 > Private IPv4 address

# ── REPLACE THESE: Match the Universal Forwarder download page ──
UF_VERSION="9.2.1"              # e.g. "9.2.1"
UF_BUILD="78803f08aabb"        # e.g. "78803f08aabb" — from the download URL
# ────────────────────────────────────────────────────────────────

# Local admin password for the forwarder agent itself (not Splunk Web)
UF_PASS="Forwarder2026!"

UF_PKG="splunkforwarder-${UF_VERSION}-${UF_BUILD}-linux-2.6-amd64.deb"
UF_URL="https://download.splunk.com/products/universalforwarder/releases/${UF_VERSION}/linux/${UF_PKG}"

echo "[1/4] Downloading Universal Forwarder ${UF_VERSION}..."
wget -q --show-progress "${UF_URL}" -O /tmp/"${UF_PKG}"
sudo dpkg -i /tmp/"${UF_PKG}"

echo "[2/4] Starting the forwarder agent..."
sudo /opt/splunkforwarder/bin/splunk start \
  --accept-license --answer-yes --no-prompt \
  --seed-passwd "${UF_PASS}"

echo "[3/4] Pointing the forwarder to the Splunk indexer..."
# This tells the forwarder where to send logs (Splunk server private IP, port 9997)
sudo /opt/splunkforwarder/bin/splunk add forward-server \
  "${SPLUNK_PRIVATE_IP}:9997" \
  -auth admin:"${UF_PASS}"

echo "[4/4] Adding log monitors..."

# Monitor Apache access log → stored in the webserver_logs index
sudo /opt/splunkforwarder/bin/splunk add monitor \
  /var/log/apache2/access.log \
  -index webserver_logs \
  -sourcetype apache_access \
  -auth admin:"${UF_PASS}"

# Monitor Apache error log → stored in the webserver_logs index
sudo /opt/splunkforwarder/bin/splunk add monitor \
  /var/log/apache2/error.log \
  -index webserver_logs \
  -sourcetype apache_error \
  -auth admin:"${UF_PASS}"

# Monitor Linux authentication log → stored in the security_logs index
# This is where SSH brute force attempts will appear
sudo /opt/splunkforwarder/bin/splunk add monitor \
  /var/log/auth.log \
  -index security_logs \
  -sourcetype linux_secure \
  -auth admin:"${UF_PASS}"

# Enable the forwarder to start automatically on reboot
sudo /opt/splunkforwarder/bin/splunk enable boot-start

echo ""
echo "================================================================"
echo "  Forwarder is active."
echo "  Sending logs  →  ${SPLUNK_PRIVATE_IP}:9997"
echo "  Monitoring:"
echo "    /var/log/apache2/access.log  →  index: webserver_logs"
echo "    /var/log/apache2/error.log   →  index: webserver_logs"
echo "    /var/log/auth.log            →  index: security_logs"
echo "================================================================"
✓
Verify the forwarder is connected

In Splunk Web (on Instance 1), go to Settings → Forwarder Management. The web server should appear as a connected client within 60 seconds of the script completing. You can also run the query below in Search & Reporting to confirm logs are arriving:

SPL — verify logs are arriving
index=webserver_logs | head 5
04

Splunk Architecture Overview

Now that both instances are running, it is useful to see how they relate to each other. The diagram below reflects exactly what you have deployed — data flows from the web server on the right, through the forwarder agent, across the private VPC network to the Splunk indexer, and up to the search interface you access in your browser.

Data Sources
Apache access logs  ·  Apache error logs  ·  auth.log
Generated on EC2 Instance 2 (webserver) at /var/log/apache2/ and /var/log/auth.log
↓   Tailed continuously by the agent on the same machine
Universal Forwarder
Lightweight agent — EC2 Instance 2 (webserver)
Compresses and transmits log data over TCP port 9997 to the Splunk server
↓   Encrypted stream over the private VPC network (172.31.0.0/16)
Indexer
Splunk Enterprise — EC2 Instance 1 (splunk-server)
Receives, parses, timestamps, and stores events in the webserver_logs and security_logs indexes
↓   SPL queries run against stored index data
Search Head
Splunk Web — EC2 Instance 1, port 8000
Dashboards, alerts, and the SPL search bar — accessed from your browser at http://<SPLUNK-PUBLIC-IP>:8000

In this workshop the Indexer and Search Head are co-located on the same instance — called a standalone deployment. This is appropriate for labs. In production, these roles run on separate dedicated servers to distribute the query load.

05

SPL Fundamentals

Search Processing Language (SPL) is the query language built into Splunk. It follows a pipeline model — each command receives the output of the previous one, separated by a pipe character (|). Run the queries below in order in Splunk Web. Go to Search & Reporting and set the time range to Last 15 minutes before running each one.

Query 1

Confirm log data is arriving

SPL
index=webserver_logs | head 20

You should see the 20 most recent HTTP requests logged by Apache. Each line is one event — one web request.

Query 2

Count events by HTTP status code

SPL
index=webserver_logs sourcetype=apache_access
| stats count by status
| sort -count
Query 3

Plot event volume over time

SPL
index=webserver_logs
| timechart span=1m count
Query 4

Extract a field from raw text using rex

The rex command extracts fields from unstructured text using named regex capture groups. This is essential for logs Splunk has not automatically parsed.

SPL
index=security_logs sourcetype=linux_secure
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| stats count by src_ip
| sort -count

06

Attack Demonstrations and Detection

The following three demonstrations simulate attack patterns a SOC analyst encounters regularly. Each follows the same structure: run the attack against the web server, then switch to Splunk Web and run the detection query to find the evidence in the logs.

⚠
Authorised use only

Run these commands exclusively against EC2 Instance 2 (webserver) within your own AWS Academy Learner Lab environment. Executing these commands against any system you do not own or have explicit permission to test is illegal. This lab exists solely for education.

Attack 1

SSH Brute Force

A brute force attack systematically tries many passwords against an authentication service. The tool hydra automates this. Every failed attempt writes a Failed password entry to /var/log/auth.log on the web server, which the forwarder ships to Splunk's security_logs index.

Run the attack from your Splunk server SSH session (Instance 1) — not your laptop and not the web server itself.

bash — paste into the Splunk server SSH session (Instance 1)
# Install hydra on the Splunk server
sudo apt-get install -y hydra

# Create a small wordlist of passwords to try
cat > /tmp/wordlist.txt << EOF
password
123456
admin
letmein
workshop
qwerty
splunk
ubuntu
EOF

# Run the brute force against the web server SSH port
# Replace <WEBSERVER-PUBLIC-IP> with the public IP of Instance 2
hydra -l ubuntu -P /tmp/wordlist.txt \
  ssh://<WEBSERVER-PUBLIC-IP> \
  -t 4 -vV 2>&1 | tail -30

Wait for hydra to finish, then switch to Splunk Web and run this detection query:

SPL — Detect SSH Brute Force
index=security_logs sourcetype=linux_secure "Failed password"
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| rex field=_raw "for (?:invalid user )?(?P<username>\w+)"
| stats
    count            as attempts
    dc(username)      as usernames_tried
    earliest(_time)  as first_seen
    latest(_time)    as last_seen
    by src_ip
| where attempts > 3
| eval duration_sec = last_seen - first_seen
| eval severity = case(
    attempts > 50, "CRITICAL",
    attempts > 20, "HIGH",
    attempts > 5,  "MEDIUM",
    true(),          "LOW")
| sort -attempts
| table src_ip, attempts, usernames_tried, severity, duration_sec
Attack 2

SQL Injection

SQL injection sends malicious SQL syntax as a URL parameter. Even when the application rejects the input, Apache logs the full request URI — including the injected payload — in /var/log/apache2/access.log. Run this from your laptop terminal.

bash — paste into your laptop terminal
# Replace <WEBSERVER-PUBLIC-IP> with the public IP of Instance 2
TARGET="http://<WEBSERVER-PUBLIC-IP>"

payloads=(
  "' OR '1'='1"
  "' OR 1=1--"
  "' UNION SELECT NULL,NULL--"
  "admin'--"
  "1; DROP TABLE users--"
  "' AND SLEEP(5)--"
  "' OR 'x'='x"
)

for payload in "${payloads[@]}"; do
  encoded=$(python3 -c "import urllib.parse,sys; print(urllib.parse.quote(sys.argv[1]))" "${payload}")
  http_code=$(curl -s -o /dev/null -w "%{http_code}" \
    "${TARGET}/login.php?user=${encoded}&pass=test")
  echo "HTTP ${http_code}  →  ${payload}"
  sleep 0.5
done
SPL — Detect SQL Injection Attempts
index=webserver_logs sourcetype=apache_access
| eval decoded_uri = urldecode(uri_query)
| where match(decoded_uri,
    "(?i)(union\s+select|or\s+1=1|drop\s+table|sleep\(|'--)")
| stats
    count             as injection_attempts
    values(decoded_uri) as payloads_used
    dc(uri_path)       as endpoints_probed
    by clientip
| sort -injection_attempts
Attack 3

Directory Traversal

A directory traversal attack uses ../ sequences — sometimes URL-encoded — to try to access files outside the web root such as /etc/passwd. These appear in Apache access logs as unusual URI patterns. Run this from your laptop terminal.

bash — paste into your laptop terminal
# Replace <WEBSERVER-PUBLIC-IP> with the public IP of Instance 2
TARGET="http://<WEBSERVER-PUBLIC-IP>"

traversal_paths=(
  "../../../../etc/passwd"
  "../../../etc/shadow"
  "..%2F..%2F..%2Fetc%2Fpasswd"
  "%2e%2e%2f%2e%2e%2fetc%2fpasswd"
  "....//....//etc/passwd"
  "/admin/../../../etc/passwd"
)

for path in "${traversal_paths[@]}"; do
  http_code=$(curl -s -o /dev/null -w "%{http_code}" "${TARGET}/${path}")
  echo "HTTP ${http_code}  →  ${path}"
  sleep 0.3
done
SPL — Detect Directory Traversal
index=webserver_logs sourcetype=apache_access
| eval decoded = urldecode(uri)
| where match(decoded, "\.\.[\\/]")
    OR match(uri, "%2e%2e|%252e|\.\.%2[Ff]")
| stats
    count           as traversal_attempts
    values(uri)    as paths_tried
    values(status) as http_responses
    by clientip
| eval risk_score = traversal_attempts * 10
| sort -traversal_attempts

Building the SOC Threat Dashboard

A SOC dashboard gives analysts a single view of current threat activity without running individual searches. The XML below creates a real-time dashboard with KPI panels, an attack timeline chart, a top attacker table, and an authentication failure log — all updating every 30 seconds.

Step 1

Create a new dashboard

In Splunk Web, click Dashboards in the top navigation, then Create New Dashboard. Set the title to SOC Threat Intelligence, select Classic Dashboard, and click Create. Once the editor loads, click Source in the top-right of the editor panel to switch to raw XML mode.

Step 2

Paste the dashboard XML and save

Select all existing content in the source editor (Ctrl+A), replace it with the XML below, then click Save.

Incident Response Workflow

Detection is only the first step. A mature SOC follows a structured process to investigate, contain, and document each incident. The table below maps each phase of incident response to the action taken in Splunk and the AWS console.

PhaseSOC ActionTool Used
1. DetectionScheduled alert fires — 10+ failed SSH attempts from one IP in 5 minutesSplunk alert configured under Settings → Alerts
2. TriageAnalyst reviews alert severity, confirms the IP is not an internal scannerSplunk dashboard — top attacker IPs panel
3. InvestigationDetermine whether any attempt succeeded and which accounts were targetedSPL query below — checks for successful logins from the attacker IP
4. ContainmentBlock the attacking IP at the security group levelAWS Console → EC2 → Security Groups → Edit inbound rules → Deny the IP
5. DocumentationRecord the timeline, affected systems, and actions takenExport SPL results to CSV; attach to ITSM ticket
6. Post-IncidentReview alert thresholds, harden SSH configuration, consider fail2banDashboard used in debrief to replay the event timeline
SPL

Check whether a brute force attack succeeded

Run this query during the Investigation phase. If the result set is not empty, a compromise may have occurred and the account should be locked immediately.

SPL — Successful Login After Failed Attempts
index=security_logs sourcetype=linux_secure
| rex field=_raw "from (?P<src_ip>\d+\.\d+\.\d+\.\d+)"
| eval outcome = case(
    searchmatch("Failed password"),   "failure",
    searchmatch("Accepted password"), "success",
    true(), "other")
| stats
    sum(eval(outcome="failure")) as failures
    sum(eval(outcome="success")) as successes
    by src_ip
| where failures > 3 AND successes > 0
| eval alert = "POTENTIAL COMPROMISE — investigate immediately"
